# Domain docs

This is a single-context project. Read the root `GLOSSARY.md` for domain terms
and relevant decisions in `docs/adr/` before work in that area. If either is
absent, continue without creating empty documents.

Use the glossary's vocabulary in specs, tickets, code, tests and reviews.
Use Matt's `domain-modeling` skill (see `workflow.md`) when terminology changes;
create ADRs for consequential trade-offs that a future contributor needs to
understand. Surface conflicts with existing ADRs explicitly. Implementation
details belong in design docs.
